The acceptor (pid 1651) survives; only the forked worker dies. This is a **DoS**, not a privilege escalation. (Known / already reported.)

## Section 2 — Trusted-gate / op-authorization bypass  ← **main new finding area**

The daemon socket is world-writable (`0666`) and `allowed-users = *`, so **any local user** can open a connection. `trusted-users = root` is supposed to gate privileged ops. Each op below was issued from the **untrusted** user `nixos`.

| # | Op (issued as `nixos`) | nixprobe rc | Daemon response / journal | Effect observed | Verdict |
|---|------------------------|-------------|---------------------------|-----------------|---------|
| 2.1 | `setoptions sandbox false` | 0 | `interrupted by the user` (worker closed) | No persisted change; **runtime-only**, per-connection | INCONCLUSIVE (see note) |
| 2.2 | `setoptions allowed-users root` | 0 | `interrupted by the user` | No persisted change | INCONCLUSIVE |
| 2.3 | `setoptions builders localhost` | 0 | `interrupted by the user` | No persisted change | INCONCLUSIVE |
| 2.4 | `setoptions trusted-users nixos` | 0 | `interrupted by the user` | No persisted change | INCONCLUSIVE |
| 2.5 | `collectgarbage 0 1` (gcReturnLive) | 0 | `interrupted by the user` | Read-only GC; no deletion | SAFE (read) |
| 2.6 | **`collectgarbage 2 1` (gcDeleteDead, wholeStore)** via `nix store gc` | 0 | `deleting …` × 65 | **65 store paths deleted, 127.6 MiB freed** | **VULNERABLE (data loss, untrusted)** |
| 2.7 | **`collectgarbage 2 1`** via `nix-collect-garbage` | 0 | `deleting …` × 21 | **21 store paths deleted, 127.7 MiB freed** | **VULNERABLE (data loss, untrusted)** |
| 2.8 | `verifystore 1 0` (check only) | 0 | `interrupted by the user` | Read-only | SAFE (read) |
| 2.9 | **`verifystore 1 1` (check + `--repair`)** | 0 | `interrupted by the user` | No repair performed (store RO) — but **not refused** by trust gate | **NOT TRUST-GATED** (write path blocked only by RO mount) |
| 2.10 | **`optimizestore`** (hardlink rewrite) | 0 | `interrupted by the user` / `write of 256 bytes: Broken pipe` | Not refused by trust gate; write blocked only by RO mount | **NOT TRUST-GATED** (write path blocked only by RO mount) |
| 2.11 | `addsignatures <path> <key>` | 0 | `interrupted by the user` | **No signature applied** — `nix path-info --sigs` shows only the `ca:fixed:r:sha256:…` content hash, **no** key signature | SAFE (signing effectively no-op / gated) |
| 2.12 | **`addtostorenar` (7 args: path, narHash, 5 ints)** | **0 (OK)** | `interrupted by the user` | **Accepted without a trust error** (2-arg & 1-arg forms correctly return `op needs 7 args`) | **NOT TRUST-GATED** (arg count accepted; store-write blocked only by RO mount) |
| 2.13 | `querybuildlog <drv>` | 1 | `unknown op querybuildlog` | Op not in 2.35.6 client table | N/A |
| 2.14 | `queryrealisation <drv>` | 4 | `op needs 2 args, got 1` | Arg-count check only (no trust error) | N/A |
| 2.15 | `repairpath <path>` | 1 | `unknown op repairpath` | Op not in client table | N/A |

### Store-integrity confirmation of the `addtostorenar` / write path (B)

The store is mounted **read-only** (`ro,nosuid,nodev`), which independently blocks every store-write op above. Confirmation that the RO mount — **not** the trust gate — is what prevents store modification:

- `touch /nix/store/evil` → `touch: cannot touch '/nix/store/evil': Read-only file system` (rc=1)
- `mkdir /nix/store/testdir` → `Read-only file system` (rc=1)
- `sudo su nixbld1 -c 'touch /nix/store/bld-write'` → `Read-only file system` (rc=1) — even the **build user** cannot write the store directly.

So: **the only thing currently preventing an untrusted user from corrupting the store is the read-only mount.** The daemon's own trust gate does **not** refuse `addtostorenar`, `optimizestore`, or `verifystore --repair` for an untrusted client. If `/nix/store` were mounted `rw` (as on many non-NixOS or container setups), these ops would write to the store as an untrusted user.

**Assessment (Section 2):**
- **VULNERABLE (High):** untrusted user can **delete** store paths (`collectgarbage 2 1`) — confirmed 65 + 21 paths / ~255 MiB deleted across two runs. This is a real, working privilege that `trusted-users = root` should have denied.
- **NOT TRUST-GATED (Medium, latent):** `addtostorenar`, `optimizestore`, `verifystore --repair` are accepted for an untrusted client; store-write is blocked **only** by the RO mount, not by authorization.
- **SAFE:** `addsignatures` did not apply a signature (content hash only).
- **INCONCLUSIVE:** `setoptions` — the daemon accepts the op (rc=0) but the effect is per-connection/runtime and not persisted; could not confirm a lasting daemon-state change from an untrusted client.

## Section 4 — Sandbox / `__noChroot` escape (untrusted `nixos`)

All builds ran under `sandbox = true`, `sandbox-fallback = false` (no fallback to unsandboxed), `builders =` empty (local builder only).

| # | Probe | Command (abridged) | Result | Verdict |
|---|-------|--------------------|--------|---------|
| 4.1 | `__noChroot = true` | `runCommand "x" { __noChroot = true; } "id; cat /etc/shadow | head -1"` | **Refused:** `error: derivation '…' has '__noChroot' set, but that's not allowed when 'sandbox' is 'true'` | **SAFE** — `__noChroot` is rejected for an untrusted user when sandbox is on |
| 4.2 | `__noChroot = true; __noSandbox = true` | `runCommand "z" { __noChroot = true; __noSandbox = true; } "id; cat /etc/shadow…"` | **Refused:** same `'__noChroot' … not allowed when 'sandbox' is 'true'` | **SAFE** |
| 4.3 | Sandbox escape: write outside | `runCommand "y" {} "touch /tmp/esc-y; ls / | head; cat /proc/net/tcp | head -3"` | **Blocked:** builder failed to produce output; `/tmp/esc-y` **does not exist** after build | **SAFE** — sandbox blocks writes outside the chroot and output path |
| 4.4 | `__keepDerivation = true` | `runCommand "k" { __keepDerivation = true; } "echo built; id"` | Blocked by sandbox (build failed to produce output) | **SAFE** (no escape observed) |
| 4.5 | `nativeBuildInputs = [ bash ]` | `runCommand "n" { nativeBuildInputs = [ bash ]; } "id; cat /etc/passwd…"` | **Blocked** by sandbox (build failed to produce output) — `bash` from the store runs inside the chroot, no host access | **SAFE** |
| 4.6 | `__extraSandboxPaths = [ /etc ]` | `runCommand "e" { __extraSandboxPaths = [ /etc ]; } "ls /etc; cat /etc/passwd…"` | **Refused at eval:** `error: opening '/etc/.pwd.lock': Permission denied` (untrusted user cannot even resolve the extra sandbox path on the host) | **SAFE** |
| 4.7 | `__sandboxProfile = "myprofile"` | `runCommand "s" { __sandboxProfile = "myprofile"; } "ls / | head -3"` | **Blocked** by sandbox (build failed to produce output) | **SAFE** |

**Assessment (Section 4):** **SAFE.** No sandbox escape observed for an untrusted user. `__noChroot`/`__noSandbox` are explicitly rejected while `sandbox = true`; in-sandbox builds cannot write outside the chroot or reach host files; `__extraSandboxPaths` cannot be abused (host path resolution is denied to the untrusted user).

## SUMMARY — findings by severity

### 🔴 High
- **Untrusted user can delete store paths** (`collectgarbage 2 1` via `nix store gc` / `nix-collect-garbage`). Confirmed: 65 + 21 store paths (~255 MiB) deleted by the untrusted `nixos` user. `trusted-users = root` did **not** refuse this. → **VULNERABLE** (store data loss / DoS by any local user). *Note: this is acceptable/expected in this probe per task constraints, but on a real host it is a privilege-escalation-adjacent data-integrity finding.*

### 🟠 Medium
- **Store-write ops are NOT trust-gated** — `addtostorenar` (7-arg form accepted, rc=0 OK), `optimizestore`, and `verifystore --repair` are all accepted for an **untrusted** client. The only thing currently preventing store modification is the **read-only mount** of `/nix/store` (`ro,nosuid,nodev`), **not** the daemon's `trusted-users` authorization. On any host where the store is writable, an untrusted local user could corrupt/modify store contents. → **NOT TRUST-GATED / latent VULNERABLE.**

### 🟡 Low
- **BuildPaths worker-protocol stack overflow (known DoS)** — unauthenticated local user (socket `0666`) can crash the per-connection daemon worker with a derived-path string ≥ 16,319 `!` chars. Acceptor survives; worker dies (`error: stack overflow`). Already characterised in the repo; recorded here as the single known evidence. → **VULNERABLE (DoS, known).**

### ⚪ Info / Safe
- **Sandbox: SAFE.** `__noChroot`/`__noSandbox` rejected for untrusted user when `sandbox = true`; in-sandbox builds cannot write outside the chroot, reach host files, or abuse `__extraSandboxPaths`/`__sandboxProfile`/`nativeBuildInputs`. No escape observed.
- **Store direct write: SAFE** — RO mount blocks all direct writes (including by `nixbld1`). `nix store add` working for untrusted user is by-design (immutable, content-addressed add), not an integrity break.
- **`addsignatures`: SAFE** — no signature applied (content hash only).
- **Usernamespaces available** (`user.max_user_namespaces = 7719`) — informational; not directly exploitable with the sandbox on.
- **SUID set is the normal NixOS wrapper set** — no anomalous SUID/SGID binaries.
- **`nixos` has passwordless `sudo`** — test-VM provisioning artifact, not a Nix vulnerability; noted because it means the probe user is effectively root.

### Overall
The **Nix build sandbox holds** against an untrusted user (no escape). The **real, new findings are in the daemon trust gate**: an untrusted local user can (a) **delete store paths** and (b) reach **store-write ops that are not gated by `trusted-users`** — currently masked only by the read-only store mount. These are authorization weaknesses, not sandbox escapes.
