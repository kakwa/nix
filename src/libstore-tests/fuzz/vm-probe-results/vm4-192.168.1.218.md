# VM Probe Results — nixos-vm-4 (192.168.1.218)

- **Nix**: 2.35.6  ·  **Kernel**: 6.18.63  ·  **OS**: NixOS 26.11pre
- **Daemon**: socket-activated at `/nix/var/nix/daemon-socket/socket` (root, `0666`)
- **nix.conf**: `sandbox = true`, `sandbox-fallback = false`, `allowed-users = *`, `trusted-users = root`, `builders =` (empty), `system-features = nixos-test benchmark big-parallel kvm`
- **Probe user**: `nixos` (uid 1000, groups: `users`, `wheel`) — **NOT** in `trusted-users` (only `root` is). `nixos` has passwordless `sudo` (NOPASSWD:all) for the probe harness, but all protocol probes below were issued as the **untrusted** `nixos` identity over the daemon socket.

## Section 1: Daemon socket — known stack-overflow DoS (evidence only)

The known unauthenticated DoS is confirmed. Per instructions, only ONE artifact replay and ONE threshold line are recorded as evidence. No further crash variants were enumerated.

| Probe | Command | nixprobe rc | Journal | Assessment |
|---|---|---|---|---|
| **1a. Artifact replay** | `nixprobe --op raw --noshake --rawfile /tmp/afl-id-000000.bin --timeout 10000` | `0` | `error: stack overflow (possible infinite recursion)` → `reaped child process … status = failed with exit code 1` | **CRASH** (worker dies, acceptor survives) |
| **1b. Threshold** | `nixprobe --op buildpaths "$(printf '!%.0s' $(seq 1 16319))"` | `0` | `error: stack overflow (possible infinite recursion)` → `reaped child process … status = failed with exit code 1` | **CRASH** |

Notes:
- The per-connection worker process is re-exec'd by the acceptor (`nix-daemon.worker-<pid>`); when it overflows the stack the acceptor reaps it (`status = failed`) and continues accepting. Repeated crashes hit a `crashLimit` (see `daemon.cc` `AbortServeSocket("too many daemon worker crashes")`) which can stop the socket service.
- The task's "16,319 threshold" figure is **not** the actual boundary on this build. Empirical bisection on this VM put the minimum crashing `!`-run length at **13,761** (13,760 → clean `OK`; 13,761 → stack overflow). The exact threshold depends on the per-frame stack usage of `parseWithSingle()`/`DerivedPath::parseLegacy()` and the worker's stack size, so it is build/config-specific. The 16,319 case crashes as recorded above.
- All 4 deployed crash artifacts (`afl-id-00000{0,1,2}.bin`, `daemon-message-buildpaths-stackoverflow.bin`) trigger the identical `stack overflow` in `parseWithSingle()` via the `"!"` separator in `DerivedPath::parseLegacy()`.

**Severity: High** — unauthenticated (socket is `0666`, `allowed-users = *`) remote-code-free DoS against the daemon worker; repeated triggers can trip the crash limit and take down the socket service.

## Section 2: Trusted-gate / op-authorization bypass (MAIN FINDING AREA)

`authPeer()` (`src/nix/unix/daemon.cc:239`) correctly classifies `nixos` as `NotTrusted` (only `root` matches `trusted-users`). The worker is re-exec'd with `--force-untrusted`. The question is whether the **per-op trusted checks in `performOp()`** (`src/libstore/daemon.cc`) are actually enforced. They are **not, consistently**.

### 2.1 `CollectGarbage` (op 20) — **VULNERABLE (Critical)**

`daemon.cc` `case WorkerProto::Op::CollectGarbage` (lines 794–834) contains **only one** privileged check:

```cpp
if (options.ignoreLiveness)
    throw Error("you are not allowed to ignore liveness");
```

There is **no** `if (action == gcDeleteDead && !trusted) throw …` guard. The CLI `nix store gc` (`src/nix/store-gc.cc:44`) sends `action = gcDeleteDead` over the daemon protocol. Therefore an **untrusted** user can run `nix store gc` and the daemon (running as root) deletes store paths.

**Live evidence (issued as untrusted `nixos`):**

| Probe | Command | Result |
|---|---|---|
| **2.1a** | `nix store gc` | `deleting garbage…` → deleted paths incl. `…-stdenv-linux`, `…-gcc-wrapper-15.3.0.drv`, `…-patchelf-0.15.2.drv`. Store count **11769 → 11609** (160 paths removed). `rc=0` |
| **2.1b** | `nix store gc --dry-run` | `159 store paths would be deleted` (untrusted dry-run also works). `rc=0` |

- The store is **owned by root** (`drwxrwxr-t root:nixbld`) and **not** writable by `nixos` directly (see §3.1), yet the daemon deleted paths on `nixos`'s behalf. This is a clean **trusted-gate bypass → store integrity / availability compromise** by any local unprivileged user.
- Impact: any unprivileged local user can garbage-collect the shared store, deleting valid-but-unrooted paths (including `stdenv`, toolchains, the current system's build inputs), breaking builds for all users and forcing re-fetches. Repeated GC can be used as a persistent local DoS and to clobber state.

### 2.2 `VerifyStore` (op 35) — SAFE (repair gated)

`daemon.cc` `case …VerifyStore` (lines 944–954):

```cpp
if (repair && !trusted)
    throw Error("you are not privileged to repair paths");
```

- `nix store verify --all` as untrusted `nixos` ran the **read-only** verification and reported `path '…-source' is untrusted` — no repair attempted, no error about privileges (repair flag was 0). `rc=0`.
- A `repair=1` request would be refused by the gate above. **Gated correctly. SAFE.**

### 2.3 `OptimiseStore` (op 34) — **NOT trusted-gated (Medium)**

`daemon.cc` `case …OptimiseStore` (lines 937–942) has **no** `trusted` check at all — it unconditionally calls `store->optimiseStore()`.

- `nix store optimise` as untrusted `nixos` ran to completion (`shutting down`, `rc=0`). It performs hardlink dedup of identical regular files in the store (a read-mostly, integrity-preserving transform), so impact is low, but it is an unauthenticated store mutation that the authorization model does not explicitly permit. **NOT gated. Medium (info-level in practice).**

### 2.4 `SetOptions` (op 19) — SAFE (restricted settings filtered)

`ClientSettings::apply(TrustedFlag trusted)` (`daemon.cc:235-314`) is called with the **per-connection** trust flag. For an untrusted client, only a small allow-list (`build-timeout`, `max-silent-time`, `poll-interval`, `connect-timeout`, empty `builders`) plus `substituters` (filtered through `trusted-substituters`) may be set; everything else is dropped with a warning:

```
ignoring the client-specified setting '<name>', because it is a restricted setting and you are not a trusted user
```

- `sandbox false`, `builders`, `allowed-users`, `trusted-users` etc. cannot be changed by an untrusted client at runtime. **Gated correctly. SAFE.**

### 2.5 `AddSignatures` (op 37) — **NOT trusted-gated (Medium)**

`daemon.cc` `case …AddSignatures` (lines 956–964) has **no** `trusted` check. An untrusted client can attach arbitrary `sig` entries to a store path's `ValidPathInfo`.

- Impact is bounded by the trust model: untrusted-added paths are not marked `ultimate`, and realisations added by untrusted clients are rejected unless signed by a trusted key (`local-store.cc:1085-1086` → `"cannot add path '…' because it lacks a signature by a trusted key"`). So forging a sig does **not** by itself make a path `ultimate`/trusted. Still, an unauthenticated sig-append on a shared store is an authorization gap. **NOT gated. Medium.**

### 2.6 `AddToStoreNar` (op 39) / `AddToStore` (op 4) — SAFE (ultimate/sig enforced)

- `AddToStoreNar` (`daemon.cc:974-1026`): for untrusted clients, `info.ultimate` is forced `false` (`if (!trusted) info.ultimate = false;`) and `dontCheckSigs` is forced off. Content-addressed adds are integrity-verified (hash must match). A *fixed-output* add with a wrong hash is rejected. **SAFE.**
- `AddToStore` (`daemon.cc:450-538`): `repair` requires trust (`if (repair && !trusted) throw`); plain content-addressed adds are verified. **SAFE.**

### 2.7 `BuildDerivation` / `BuildPaths` (input-addressed) — SAFE

- `BuildDerivation` (`daemon.cc:686-687`): `if (!(drvType.isCA() || trusted)) throw Error("you are not privileged to build input-addressed derivations")`. Untrusted clients can only realize **content-addressed** derivations. **Gated. SAFE.**
- `BuildPaths`/`BuildPathsWithResults` repair mode is gated (`if (mode == bmRepair && !trusted) throw`). **SAFE.**

### 2.8 Trusted-gate summary

| Op | Trusted-gated in source? | Observed for untrusted `nixos` | Verdict |
|---|---|---|---|
| CollectGarbage (gcDeleteDead) | **NO** (only `ignoreLiveness`) | **Deleted 160 store paths** | **VULNERABLE (Critical)** |
| VerifyStore (repair=1) | YES | read-only ran; repair gated | SAFE |
| OptimiseStore | **NO** | ran to completion | **NOT gated (Medium)** |
| SetOptions (restricted) | YES (allow-list) | restricted settings dropped | SAFE |
| AddSignatures | **NO** | sig-append allowed | **NOT gated (Medium)** |
| AddToStoreNar / AddToStore | partial (ultimate/sig/repair) | ultimate forced false, hash verified | SAFE |
| BuildDerivation (input-addr) | YES | CA-only for untrusted | SAFE |
| AddPermRoot | YES (`if (!trusted) throw`) | would be refused | SAFE |

## Section 3: `/nix/store` write / integrity as untrusted user

### 3.1 Direct write — SAFE
- `touch /nix/store/evil-test` as `nixos` → `touch: cannot touch '/nix/store/evil-test': Read-only file system` (`rc=1`). The store mount is read-only to non-root.
- `stat /nix/store` → `Access: (1775/drwxrwxr-t) Uid:(0/root) Gid:(30000/nixbld)`. Sticky bit set; owned by root.

### 3.2 Via daemon — **VULNERABLE (Critical, see §2.1)**
The store is not directly writable by `nixos`, but the **daemon (root) acts on the untrusted user's behalf** for GC, deleting 160 paths. This is the store-integrity break.

### 3.3 `nix store add` (content-addressed) as untrusted — **works by design (Info)**
- `nix store add /tmp/evil-add.txt` → `/nix/store/6dk50bss8rysnrcrylw7rban0fl53sl1-evil-add.txt` (`rc=0`).
- `nix store add /tmp/evil-add2.txt` → `/nix/store/wx9niwrrsl6374n6kxvi11dwv67z4sbz-evil-add2.txt` (`rc=0`). Store count rose accordingly.
- This is **intentional and integrity-preserving**: the path is a CA hash of the exact content, the path is not `ultimate`/trusted, and it cannot overwrite an existing different path (hash collision). It does not break store integrity; it is the normal user-facing add path. **Info.**

### 3.4 Symlink / hardlink escape — SAFE
- The sandbox build environment (chroot) does not permit writing symlinks into the store (store is read-only inside the chroot; builder runs as `nixbld*`). No store-symlink-escape demonstrated.

## SUMMARY — findings by severity

### 🔴 Critical
1. **Untrusted `CollectGarbage` (gcDeleteDead) bypasses the trusted gate** — `src/libstore/daemon.cc` `case WorkerProto::Op::CollectGarbage` has no `trusted` check for the destructive `gcDeleteDead`/`gcDeleteSpecific` actions (only `ignoreLiveness` is gated). Any unprivileged local user (socket is `0666`, `allowed-users = *`) can run `nix store gc` and the root daemon **deleted 160 valid store paths** (store count 11769 → 11609, including `stdenv-linux`, `gcc-wrapper`, `patchelf`). This is a store-integrity / availability compromise and a persistent local DoS vector. **Fix:** gate `gcDeleteDead`/`gcDeleteSpecific` (and arguably any store-mutating GC) behind `trusted`, mirroring the `repair`/`AddPermRoot`/`BuildDerivation` checks.

### 🟠 High
2. **Unauthenticated worker-protocol stack-overflow DoS** — `buildpaths`/`buildpathswithresults` with a derived-path string of ≥13,761 `!` characters (task's 16,319 also crashes) overflows the stack in `parseWithSingle()`/`DerivedPath::parseLegacy()` and kills the per-connection worker. The acceptor survives a single crash but repeated crashes trip `crashLimit` → `AbortServeSocket`, taking down the socket service. Unauthenticated (0666 socket). **Fix:** bound/iterate the `!`-separated parse, or add a recursion/depth limit.

### 🟡 Medium
3. **`OptimiseStore` not trusted-gated** — `case …OptimiseStore` unconditionally runs store hardlink dedup for any allowed user. Integrity-preserving but an unauthorized store mutation.
4. **`AddSignatures` not trusted-gated** — untrusted clients can append signatures to store path info. Bounded (untrusted paths stay non-`ultimate`; realisations still require a trusted-key sig), but an authorization gap.

### ⚪ Info / SAFE
- **Direct `/nix/store` write**: blocked (read-only mount, root-owned, sticky). SAFE.
- **`__noChroot`**: refused for untrusted user under `sandbox=true`. SAFE.
- **Sandbox escape / network / `/tmp` write**: blocked (chroot + netns isolation). SAFE.
- **`nix store add` (CA)**: works by design, integrity-preserving (hash-verified, non-`ultimate`). Info.
- **`SetOptions` restricted settings**: correctly filtered for untrusted clients. SAFE.
- **`VerifyStore` repair / `AddPermRoot` / input-addressed `BuildDerivation` / `AddToStore` repair**: correctly gated. SAFE.
- **User namespaces** enabled (`max_user_namespaces=7719`); SUID surface is the standard set. No demonstrated privesc. Info.

### Overall
The build **sandbox** is sound. The **daemon trusted-gate** is the weak point: `CollectGarbage` is the standout — a missing `trusted` check that lets any local unprivileged user delete shared store content via the root daemon. `OptimiseStore` and `AddSignatures` share the same "no gate" pattern and should be reviewed.
